## 二、三层法讲项目（被深挖时用）

### 第一层：架构总览（先讲这个，让对方有全局）
| 层 | 组件 | 作用 | 类比 |
|---|---|---|---|
| 容器底座 | K8s 集群(1主2从) | 编排调度 | 大楼（管理所有单元） |
| 镜像仓库 | Harbor | 存/拉镜像 | 仓库 |
| 存储 | NFS + PV/PVC | 数据持久化 | 仓储（不随住户消失） |
| 业务 | MySQL / Tomcat / Nginx | 前台/后端/中间件 | 住户 |
| 接入层 | Nginx 反代(ConfigMap) | 统一入口、按路径转发 | 大门保安（分流） |
| 自动化 | GitLab + Runner CI/CD | 自动构建+部署 | 自动送货上门 |

一句话：**K8s 当底座，Harbor 管镜像，NFS 管数据，业务容器化，Nginx 做入口，CI/CD 全自动**。

### 第二层：部署细节（怎么搭，讲关键命令）
- 集群：`kubeadm init`(改镜像源+网段+cri-socket) → `kubeadm join` → `kubectl apply -f kube-flannel.yml`
- Harbor：`docker-compose` 跑（约10容器），http 模式
- 存储：master 配 NFS(`exportfs`)，node 挂载；业务用 PV/PVC(绑定 NFS)
- 业务：RC/Deployment + Service(NodePort) + PV/PVC；镜像 push 到 Harbor
- 入口：ConfigMap 存 nginx 配置 → Deployment 反代(proxy_pass 到 tomcat-svc)
- CI/CD：GitLab(仓库+流水线) + Runner；`.gitlab-ci.yml` 三阶段 build→push→deploy

### 第三层：原理追问（为什么——最考验，提前备）
- **为什么 flannel 依赖 br_netfilter**？→ 桥接流量(overlay)要过 iptables/内核转发，缺模块则 Pod 间通讯不了
- **为什么 PV 用 RWX + Retain**？→ 多节点共享读写 + 删除 PVC 不丢数据
- **为什么 push 要 insecure-registries**？→ docker 只信 https,Harbor 是 http,不信任就拒绝
- **为什么 CI 里 kubectl 要 kubeconfig**？→ kubectl 靠配置文件连集群,CI 用户没配就连 localhost:8080
- **为什么 CI 里 docker build 要用 registry-mirrors**？→ build 是 BuildKit 拉镜像,不走 daemon 代理,直连被墙

## 三、排障案例（STAR，挑 2-3 个当王牌）

### ⭐ 案例1：Flannel CrashLoopBackOff → br_netfilter
- **S(背景)**：主节点 kubeadm init 后装网络插件 Flannel,但 Pod 一直 CrashLoopBackOff
- **T(任务)**：定位为什么 flannel 起不来
- **A(行动)**：先 `kubectl describe` 看事件、`kubectl logs` 看日志,发现报 `Failed to check br_netfilter: stat .../bridge-nf-call-iptables no such file`——判断是**内核缺 br_netfilter 模块 + 内核参数没开**,于是 `modprobe br_netfilter` + `sysctl` 开 ip_forward / bridge-nf-call-iptables/ip6tables + 写配置持久化 + rollout restart
- **R(结果)**：flannel 正常,集群 Ready
- **亮点**：排查靠"先看事件和日志,别猜"——这套方法论是加分项

### ⭐ 案例2：nginx Pod 一直 ContainerCreating → NFS 目录没导出
- 现象：nginx Pod 卡 ContainerCreating 2 天,mysql/tomcat 正常
- 排查：`kubectl describe` 看 Events → `mount.nfs ... No such file or directory`
- 根因：NFS 服务端 **/data/k8s/nginx 目录没建/没 exportfs -rv**
- 修复：master 建目录 + `exportfs -rv` 重新导出,kubelet 自动重试挂载恢复
- 亮点：NFS 新共享目录必须重新 exportfs,客户端才知道——经典存储排障

### ⭐ 案例3：CI/CD 一整串坑（最能体现排障+工程能力）
- token 被省略/403 → 用 runner register 自己生成
- runner Pending → run_untagged / 配置
- git clone 失败 → hosts 解析 gitlab-server
- docker 权限 → gitlab-runner 加 docker 组
- build 拉镜像被墙 → BuildKit 用 registry-mirrors
- push 到 Harbor → insecure-registries + admin 账号
- deploy kubectl → kubeconfig 放对用户 + KUBECONFIG
- **亮点**：从 0 把 CI/CD 管道调通,全是"踩坑→看日志→定位→解决",证明你对云原生 CI/CD 有真动手能力
